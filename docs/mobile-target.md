# Mobile target: regrowing an app as Expo

This is the contract between the Theseus engine, the builder agent that regrows an app as a native
Expo app, `@theseus/mobile` (which builds, installs and launches it) and Kane CLI (which verifies it
on the Android emulator and the iOS simulator).

## 1. Builder brief

Paste this section into the builder agent's workspace next to `SPEC.md`.

> You are building a native mobile app with Expo that reproduces every behavior in `SPEC.md`. The
> app will be compiled into a standalone release build (no Metro, no Expo Go, no dev client) and
> tested by an automated agent that sees the screen and the accessibility tree and acts like a user.
>
> **Stack.** Expo SDK 58 (`expo ~58.0.26`, `react-native 0.88.1`, `react 19.3.0`), TypeScript strict.
> Install every native dependency with `npx expo install <pkg>` so versions match the SDK. Allowed
> native modules: `@react-native-async-storage/async-storage`, `react-native-safe-area-context`,
> `expo-status-bar`. Pure JS packages are fine; do not add other native modules.
>
> **Project structure (produce exactly this at the workspace root):**
>
> ```
> package.json        name, "main": "index.ts", scripts below, a committed package-lock.json
> app.json            expo.name, expo.slug, expo.android.package, expo.ios.bundleIdentifier
> index.ts            registerRootComponent(App)
> App.tsx             root component wrapped in <SafeAreaProvider>
> src/                screens, components, storage, pure state logic
> assets/             icon.png, adaptive icon images
> tsconfig.json       extends expo/tsconfig.base, "strict": true
> ```
>
> Do not create or commit `android/` or `ios/`; they are generated by `npx expo prebuild`. Do not add
> `expo-dev-client`, `expo-updates` or any config plugin that needs credentials.
>
> **Scripts.** `"start": "expo start"`, `"typecheck": "tsc --noEmit"`. Theseus builds with
> `npm ci` then `npx expo prebuild` then Gradle `assembleRelease` / `xcodebuild -configuration Release`.
> Before you finish a round, `npm ci && npx tsc --noEmit && CI=1 npx expo prebuild --no-install`
> must succeed with no prompts.
>
> **Persistence.** Everything the web app kept in `localStorage` lives in AsyncStorage under one
> key per collection, as JSON. Load once on mount; do not write until that load has finished
> (otherwise the empty initial state overwrites saved data). Write on every change. Behaviors that
> say "reload the page" are run as "close and reopen the app", and must show the same data.
>
> **No network.** No `fetch`, no analytics, no remote fonts or images, no Expo Updates. Everything
> ships in the binary. The app must work in airplane mode.
>
> **No permissions, no system dialogs.** Do not request camera, location, notifications or
> tracking. Do not use `Alert.alert` for confirmations the web app did not have.
>
> **Accessibility is how the test agent finds things.** For every interactive element:
>
> - Keep the web app's visible copy exactly (placeholder `What needs to be done?`, button text
>   `Clear completed`, filter names `All`, `Active`, `Completed`, counter `2 items left`).
> - `accessibilityLabel` = the visible text, or for icon-only controls the action plus its target:
>   `Delete Buy milk`, `Toggle Buy milk`, `Mark all as complete`.
> - `accessibilityRole`: `button`, `checkbox` (with `accessibilityState={{ checked }}`), `header`,
>   `text`. Selected filter gets `accessibilityState={{ selected: true }}`.
> - `testID` in kebab-case matching the web app's class or id where one exists (`new-todo`,
>   `todo-count`, `clear-completed`, `toggle-all`).
> - Never hide a control behind hover. Controls the web app reveals on hover (the destroy `x`) are
>   always visible. Targets are at least 44x44 points.
>
> **Input.** Text fields submit on the keyboard's return key (`onSubmitEditing`,
> `submitBehavior="submit"`, `returnKeyType="done"`), trim input and ignore empty submissions like
> the web app. Editing an item (web: double-click) is a double tap on its label, which shows a text
> field that saves on submit or blur and cancels on Android back. Escape has no mobile equivalent;
> blur without changes cancels.
>
> **Layout.** Portrait phone, safe areas respected, content scrolls when the keyboard is open
> (`KeyboardAvoidingView`), nothing clipped on a 6.1" screen. Light mode only.
>
> **Done means** the app launches from a cold install to its first screen with no red box, no
> yellow box, no network, and every behavior in `SPEC.md` can be performed by tapping and typing.

## 2. How Theseus builds and runs it

`@theseus/mobile` (see `packages/mobile/src/index.ts`):

| Step | Android (`--target emulator`) | iOS (`--target simulator`) |
|---|---|---|
| `ensureDevice(platform)` | boots an AVD (`THESEUS_AVD`, else a running one, else the first) and waits for `sys.boot_completed` | boots a simulator (`THESEUS_SIMULATOR`, else a booted iPhone, else the first iPhone on the newest runtime) and waits on `simctl bootstatus` |
| `buildExpo(dir, platform)` | `npm ci` if needed, `expo prebuild --platform android`, `./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a` with JDK 17, signed with the debug keystore | `expo prebuild --platform ios`, `pod install`, `xcodebuild -configuration Release -sdk iphonesimulator ARCHS=arm64`, then `ditto -c -k --keepParent` |
| Artifact (`appPath`, what `--app` takes) | `android/app/build/outputs/apk/release/app-release.apk` | `ios/build/<Name>.zip` (the `.app` at the zip root) |
| Standalone check | fails unless the APK contains `assets/index.android.bundle` | fails unless the `.app` contains `main.jsbundle` |
| `installApp` / `uninstallApp` / `launchApp` | `adb install -r` (uninstall and retry on a signature change), `adb uninstall`, `am start -W` on the resolved LAUNCHER activity | `simctl install` (expands a `.zip`), `simctl uninstall`, `simctl launch` |

Every failure is a `MobileError` with a `code` (`no-avd`, `java-missing`, `cocoapods-missing`,
`signing-failed`, `build-failed`, `device-boot-timeout`, ...), a `remedy`, and the relevant log tail.
Build output streams through `onLog`.

Kane invocation per behavior (one at a time, never in parallel):

```bash
kane-cli run "<objective>" --agent --target emulator  --app <apk> --device-name <AVD name> --os-version <Android release, e.g. 15> < /dev/null
kane-cli run "<objective>" --agent --target simulator --app <zip> --device-name "iPhone 18 Pro" --os-version 27.2 < /dev/null
```

`--device-name` and `--os-version` are required in `--agent` mode unless saved with
`kane-cli config set-device-name` / `set-os-version`; without them the run exits 2. Pass the
`deviceName` and `osVersion` that `ensureDevice` returns. (The invocation in `docs/plan.md` omits
them.)

## 3. Mapping web objectives to native

Behaviors stay platform-neutral in `SPEC.md`. Kane's driver interprets the objective against what is
on screen, so most web phrasing works unchanged. These are the phrases that need a native meaning;
the builder brief above makes each of them possible, and the engine may append the right-hand
column as a hint when it runs a behavior on a mobile target.

| Web phrasing | Native meaning |
|---|---|
| Open the app / go to the URL | The app is already launched by Kane; start from its first screen |
| Reload the page / refresh | Close the app and open it again (persisted state must survive) |
| Navigate to `#/active`, click the Active link | Tap the `Active` filter |
| Press Enter | Tap the keyboard's return key |
| Double-click the todo | Double tap the todo's label |
| Hover over the todo and click the x | Tap `Delete <title>` (always visible) |
| Press Escape | Tap outside the field without saving, or press Android back |
| The page title / the document title | The header text |
| localStorage contains ... | Not observable; assert what the screen shows after relaunch instead |
| Browser back button | Android back gesture; no equivalent on iOS, so avoid it in shared behaviors |

## 4. Kane mobile limitations that shape this target

From Kane CLI 0.10.7 docs (`references/mobile.md`, `docs/user-guide/mobile/*`, `testrun.md`,
`testmd/overview.md`) and what we observed on this machine:

- **App only, no mobile web.** A mobile run always drives an installed app. `--url` is not used and
  there is no mobile browser target. WebViews inside an app are handled.
- **Formats.** `emulator` takes an `.apk`; `simulator` takes a `.zip` of the `.app`. A bare `.app`,
  a package or bundle id, and an `.ipa` on a simulator are all refused. Real devices take
  `.apk`/`.aab` and `.ipa`. An uploaded `APP<digits>` id works everywhere.
- **Every local build is uploaded to the account** on first use (cached per machine by content), and
  the run prints its `APP...` id. Rebuilt artifacts are new uploads.
- **Local runs need macOS on Apple Silicon** and an `arm64-v8a` AVD. We build only `arm64-v8a`; add
  `androidAbis` if a grid device ever needs `x86_64`.
- **One at a time.** Local suites with any emulator or simulator member require `--parallel 1`;
  larger values are refused. Run Android and iOS behaviors sequentially, never concurrently.
- **App state between runs.** Kane installs the app and resets it per run unless the `_test.md` sets
  `no_reset: true` (not allowed on real devices). Each behavior therefore starts from a fresh app,
  which matches a fresh browser profile on web. A "reload" inside one objective is a relaunch
  within the same session, so AsyncStorage persists across it.
- **Deep links** exist only as replay-only `@deeplink` headings in `_test.md`; do not rely on them in
  objectives. The app should not need a deep link to reach any behavior.
- **Permissions and alerts.** `config set-auto-grant-permissions` (Android) and
  `config set-auto-accept-alerts` (iOS) default to on. Our apps request nothing, so this only
  matters if a builder adds a permission by mistake.
- **Device selection is explicit in agent mode** (see section 2). Adaptive heal on replay works on
  emulator and simulator, not on real devices.
- **Managed tooling is a blocker today.** `kane-cli doctor --target emulator|simulator --install`
  on this machine (kane-cli 0.10.7, not logged in) fails with
  `No managed mobile dependencies are published for darwin-arm64-emulator (kane-cli 0.10.7). This is a packaging gap ... or pass --appium-url to use an Appium server you manage yourself.`
  Retry after `kane-cli login`; if it still fails, the fallback is a self-managed Appium server with
  the `uiautomator2` and `xcuitest` drivers and `--appium-url` (not in `--help`, mentioned only by
  that error).
